# 收入模块核心设计与数据流

本文档旨在统一、澄清和收敛 `/doc` 目录下的多个产品与实施文档（`prd.md`, `prd-income.md`, `prd-income-implementation-plan.md`），并结合 `prisma/schema.prisma` 的最终实现，为收入模块提供一个单一、明确的事实来源（Single Source of Truth）。

## 1. 核心目标与原则

- **数据源唯一性**：所有收入相关的计算和预测逻辑**全部在服务端**完成。前端（Next.js + SWR）仅负责展示由 API 返回的数据。
- **核心实体 `IncomeRecord`**：`IncomeRecord` 表是所有月度收入计算结果的**唯一存储位置**。无论是历史数据、当前月份，还是未来预测，都以记录的形式保存在此表中。UI 上展示的所有“概览”、“时序”或“记录”，其数据源均为此表。
- **输入与输出分离**：用户或管理员操作的是**计算输入**（如工资变更、奖金、城市规则），而不是直接修改计算结果。系统响应这些输入，通过**自动化的回算过程**来更新 `IncomeRecord`。
- **页面功能不冗余**：除 `Dashboard` 作为全局信息聚合入口外，任何功能页面应有自己清晰独立的职责，**避免信息重复展示**。

## 2. 核心概念澄清

针对您提出的混淆点，这里进行明确定义：

### 自动年度回算（Automated Recalculation）

**年度回算是一个自动化的内部数据对齐工具，而非报税工具。**

它的核心职责是：当任何影响收入计算的**输入**发生变化时（例如，用户补录了去年的工资变更、管理员更新了社保基数），系统会自动为所影响的年份创建一个**异步回算任务**。

- **自动化与延迟执行**：任务不会立即执行，而是会**延迟10分钟**。如果在这10分钟内，用户对同一年份的输入进行了多次修改，这些修改会**合并成一个回算任务**，避免了资源浪费。
- **手动触发**：系统依然提供“立即回算”的选项，供需要即时看到结果的用户使用。
- **任务状态追踪**：会有一个专门的 UI 界面（例如在 `/income/recalc-status`），用于展示所有回算任务的**状态**（排队中、运行中、已完成、失败），确保过程的透明性。

### 收入页面 (`/income`) 的整合视图

根据“页面功能不冗余”原则，原 `/reports/income` 页面被移除，其功能被整合进 `/income` 页面。现在，`/income` 页面是管理和分析收入的**唯一中心**，它包含以下视图：

1.  **收入概览 (Overview)**
    - **功能**: 对指定时间范围内的 `IncomeRecord` 数据进行**聚合 (Aggregation)**。它展示的是**累计值**，如“年度累计税前收入”、“平均月薪”、“总计个税”等。回答的是“我这段时间总共挣了多少钱？”的问题。

2.  **收入时序 (Timeseries)**
    - **功能**: 将 `IncomeRecord` 中的月度数据进行**可视化**，通常以折线图或柱状图展示。它关注的是**趋势与变化**，如“税后收入的逐月走势”、“个税在哪个月份有较大波动”。（此功能从原 `/reports/income` 移入）

3.  **月度收入记录 (Monthly Records)**
    - **功能**: **直接展示** `IncomeRecord` 表中的每一条记录，包含所有计算的中间值和最终值（如当期应税、累计应税、社保、公积金、个税等），用于**对账和审计**。
    - **关于“只能看不能改”**：这个设计是刻意的。用户不应直接修改一个计算结果。正确的做法是：
        - **修改输入**：去修改工资、奖金等原始数据，然后**等待系统自动回算**或**手动触发立即回算**。
        - **人工调整**：如果确实需要覆盖计算结果，系统提供了“人工调整”功能。这会在 `IncomeRecord` 中记录一个 `manual` 来源的标记，并优先使用人工录入的值，同时在 UI 上明确提示此数据为人工覆盖。

## 3. 数据流与生命周期

这是一个完整的收入数据处理流程：

1.  **输入 (Inputs)**
    - **用户**: `IncomeChange`, `BonusPlan`, `LongTermCashPlan`, `EquityGrant`, `UserAnnualDeduction`, `CityChangeRecord`。
    - **管理员**: `CityRuleSS`, `CityRuleHF`, `TaxConfig`, `TaxBracket`。

2.  **处理 (Processing) - 异步任务化**
    - 当任意“输入”被创建、更新或删除时，后端自动为受影响的 `userId` 和 `taxYear` 创建或更新一个**回算任务** (`RecalculationTask`)。
    - 该任务被设置为10分钟后执行。如果已存在一个针对同一 `userId` 和 `taxYear` 的待处理任务，则重置其计时器，实现**去抖 (Debouncing)**。
    - 一个后台工作进程 (Worker) 定期检查并执行到期的任务。

3.  **计算 (Calculation)**
    - Worker 进程拾取任务后，启动 `IncomeRecalculationService`。
    - 服务端**按月循环**（从 1 月到 12 月），严格按照累计预扣法，一步步计算所有收入和税务相关字段。

4.  **存储 (Storage) - 单一事实来源**
    - 计算出的**所有字段**都被写入或更新到对应月份的 `IncomeRecord` 表中。
    - 如果是未来月份，记录的 `isForecast` 字段会被标记为 `true`。

5.  **展示 (Presentation)**
    - 前端所有相关页面 (`/dashboard`, `/income`) 通过 SWR hook 调用 API 端点。
    - 这些 API 端点**仅从 `IncomeRecord` 表中读取数据**。
    - 回算成功后，SWR 的缓存会失效并自动重新获取数据，UI 随之更新。

## 4. 总结

| 概念 | 存储/逻辑实体 | 作用 | UI 页面 |
| :--- | :--- | :--- | :--- |
| **输入** | `IncomeChange`, `BonusPlan`, etc. | 定义计算的原始参数 | `/income` (表单), `/rules/cities` |
| **处理** | `RecalculationTask` (异步任务) | 自动、防抖地触发数据重新生成 | `/income/recalc-status` (任务监控) |
| **结果** | `IncomeRecord` | **唯一事实来源**，存储月度计算快照 | (所有页面的数据源) |
| **整合视图** | `IncomeRecord` (聚合+可视化+列表) | 聚合、趋势分析、对账 | `/income` |

通过这套优化的设计，系统不仅确保了数据的一致性和可追溯性，还通过自动化和页面整合，极大地提升了用户体验和系统效率。
